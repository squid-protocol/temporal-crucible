# Which changes move the engine's output, quality and speed? Structure-function plan on GitGalaxy's own history (fixed 2026-11-20 evening, before any of these numbers were computed; EXPLORATORY)

Owner question: we started with engine quality (functions found per language) and speed; do structure changes that we can see correlate with them; do we have causes for the speed-ups; can we do the same for the language function enhancements; use the data we have to find structure-function relationships with dependent variables we can measure.

## Dependent variables we hold (engine output and quality)
1. Speed: CPU seconds of each commit's own engine on four pinned corpora (done: 35 localised steps; `docs/self_speed/final/`).
2. Output volume of the same runs on language-crucible: functions found, call edges and files mapped (284 runs from the sensitivity pass; the pilot runs predate the field).
3. Quality per language against tree-sitter, measured by the repo's own CI on the pinned crucible and committed: `docs/self_scan/tree_sitter_accuracy_history.csv` (9,194 rows, 53 languages, one row per language per measured commit from 2026-08-11: real, found and extra functions, function and class recall and precision, argument match), and the per-language baselines `tests/tree_sitter_accuracy_baseline_<lang>.json` (30 languages, 154 baseline commits). Also `call_resolution_history.csv` (1,850 lines), `graph_coverage_history.csv` (442) and `ground_truth_history.jsonl` (10,825).
## Independent variables (what a change looks like)
Per first-parent commit: files changed by kind (core, standards, translator_tools, tests, docs), which language rule file(s) `gitgalaxy/standards/language_standards/languages/<lang>.py` changed, which core files changed (prism.py, detector.py and other core/), engine functions touched (diff cache), lines added and deleted, count of regex rules in a changed language file (static, from the file at that commit), the squash subject, PR title, labels and body.

## Questions and what would answer them (declared now)
- Q1 (does speed co-move with output volume?). Across consecutive sampled commits on language-crucible (n about 283 pairs), Spearman correlation between the change in log CPU and the change in log functions found. Primary excludes pairs where files mapped changes by more than 3% (the file screen); all pairs also shown. Predicted: rho at least 0.3. Refuted if rho is 0.1 or below.
- Q2 (are speed-ups pure?). For each of the 12 down-steps, re-time the parent and the found commit with output counts (language-crucible and keyword-rosetta). A speed-up is PURE if functions found changes by less than 2% and files mapped by less than 3%. Predicted: at least half of the down-steps are pure. Reported for up-steps too.
- Q3 (causes of the steps). Two models classify the mechanism of each of the 35 events from the commit text and diff summary only (never the size or direction of the step): optimisation (algorithm, regex, prefilter, caching, precompile), file-screen or skip rule, new feature or rule, correctness fix, refactor or restructuring, infrastructure or other, unknown. Predicted: at least half of the down-steps are classified as optimisation. Compared with the observed direction afterwards.
- Q4 (attribution of quality steps). A quality step = two consecutive history rows for one language where function recall moves by at least 1.0 percentage point or functions found by at least 5%. The window = the first-parent commits between the two measured commits. Q4a: in at least 60% of quality steps the window contains a commit touching that language's own rule file. Q4b: report how many measured commits move five or more languages at once (engine-wide change) and what they touch (core files). Where a window holds one such commit it is the candidate cause; where it holds several they are listed and, for the few steps that matter, localised by re-running that language's corpus folder (one folder scans in seconds).
- Q5 (cost of quality). For commits that are both a localised speed event and inside a quality-step window, report the sign relation of the speed change and the quality change (counts, no threshold).
- Q6 (structure of the rules and quality). Within a language over time, the change in the number of regex rules in its rule file between measured commits against the change in functions found or recall (Spearman, across steps; predicted at least +0.2); and across languages at the tip, rule count and rule-file size against recall (reported).
Everything is exploratory and descriptive (no multiplicity control); the quality series is the repo's own, measured by its CI at pushes that moved a language, so unchanged commits have no row.

## Independence of the cause labels
Mechanism labels (Q3) come from the text and the change summary only; the step size and direction are withheld and compared afterwards. Two different models label independently; agreement is reported.

## What we cannot do with this data
Per-language function counts for engine versions we did not scan (only the CI's history from 2026-08-11, plus two whole-repo scans and the tip's per-folder scans); anything about languages without a baseline (23 of 79); causal claims.
