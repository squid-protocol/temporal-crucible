# Control repository — build specification, phase 1

**Purpose.** A generated git repository whose truth we planted, so the study pipeline can be run on something
with a known answer. It is the positive and negative control the SA3 studies never had. Phase 1 builds the
generator, its ground-truth manifest, its mutations and its own tests. Phase 2 (a separate spec, after review)
runs the SA3 pipeline on it and scores the pipeline against the manifest.

**Revision 2, 2026-11-14, after the first review** (`docs/process/reviews/control_repo_review_fable.md`). Changed:
expected positives are given for the snapshot's unit files only; two more cases go under `ambiguous`; the
change effect must rest on at least 40% of files; inserted renames do not rewrite callers; test 5 states its
file count and tolerance; `reverts_of_new_code` is worded as it can be built. Each change is marked **[r2]**.

**Who builds, who reviews.** Built from this document alone by one session; reviewed by a different model.
Where this document is silent, the builder writes the choice into `DECISIONS.md` rather than guessing silently.

## Deliverables

```
tools/control_repo/
  generate.py        the generator (CLI below)
  codegen.py         source-file generation with planted structure, per language
  history.py         the commit timeline
  mutations.py       named variants
  manifest.py        ground-truth schema, writer, loader
  README.md          how to use it, in plain language
  DECISIONS.md       every choice this spec did not make
tests/test_control_repo.py
```

Nothing else in the repository is edited. No commits, no pushes: leave the work in the working tree.

## CLI

```
python tools/control_repo/generate.py --out DIR --seed N [--language python|c] [--files 400]
        [--effect NAME=BETA ...] [--mutation NAME ...] [--years 4] [--profile small|default]
python tools/control_repo/generate.py --list-mutations
```

- `DIR/repo/` is a normal (non-bare, full, not partial) git repository. `DIR/manifest.json` is the truth.
- **Deterministic:** the same arguments give the same commit hashes. Fix author, committer, dates, and the
  environment of every git call (`GIT_AUTHOR_*`, `GIT_COMMITTER_*`, `TZ=UTC`, `GIT_CONFIG_NOSYSTEM=1`, a
  private `HOME`); no dependence on the machine's git identity or time.
- No network. No reading of any other repository. Run git with `gc.auto=0`.
- `--profile small` (about 60 files, 300 commits) generates in under ten seconds for tests.
- **[r2]** For phase 2: `--years 4` leaves about 270 days after the snapshot, less than SA3's 730-day window,
  and `--profile small` is below SA3's floors. A pipeline run needs the default profile or larger and a span
  that leaves 730 days after the snapshot (`--years 10`).

## What the repository contains

**Layout.** Directories of uneven size (a few big, many small, nested two to three deep) under `src/`, plus:
`tests/` (test files), `vendor/thirdparty/` (imported code), `docs/`, one generated file with a
"generated by" header, a `.gitattributes` that marks one directory `linguist-vendored` and one path
`export-ignore`, and a top-level licence file. The manifest says, per file, which of these it is — and
therefore whether a correct study should rank it (`is_unit: true/false`, with the reason).

**Files with planted structure.** Each unit file is generated code that parses and is plausible: functions
with bodies, calls to functions in other files, conditionals, loops, assignments. Per file the generator
fixes, and the manifest records:

| planted property | meaning | what a correct instrument should report |
|---|---|---|
| `loc` | total lines | the file's line count |
| `branches` | number of `if` / loop / switch-like constructs | the engine's branch-keyword count, exactly or by a stated mapping |
| `max_nesting` | deepest control nesting, with else-if chains counted flat | `nest_max` from `tools/sa3_nesting.py` |
| `calls_in`, `calls_out` | calls from / to functions in other files | resolved call counts |
| `state_writes_in_branches` | assignments to non-local state inside a conditional | the engine's branch-state measure |
| `busyness` | latent: how often ordinary work touches the file | not observable; drives the history |

Sizes are heavy-tailed (lognormal, with many small files and exact ties). Properties are correlated with size
the way real ones are: counts roughly proportional to `loc` times a per-file density drawn independently.
Record the density as well as the count.

For `--language c`, also plant pointer and allocation operations so that a risk-style score has something to
see. For `--language python`, say in the manifest that it does not.

## The history

A first-parent mainline over `--years`, default four, with a **snapshot point at 80% of the commits** recorded
in the manifest (hash, time), and a second point 365 days before it.

Every commit has a true type in the manifest:

| type | what it does | how it is written |
|---|---|---|
| `ordinary` | edits 1–10 files, chosen with probability rising in busyness and size | plain messages |
| `fix` | edits the file(s) carrying a defect | **one of several conventions, recorded per commit**: `Fixes #N`; a `Fixes:` trailer naming a hash; a CVE id; a Jira-style key; a bare keyword ("fix crash in parser") with no reference; and *no signal at all* (a silent fix) |
| `feature_with_ticket` | ordinary work that names a ticket: "Fixed #N -- Added …" | looks like a fix to a naive label; is not one |
| `revert` | reverts an earlier commit; record whether its target is before or after the snapshot | "This reverts commit <hash>" |
| `sweep` | touches most files: licence header, reformat | some worded "Fix lint", some not |
| `rename`, `delete`, `add` | moves, removes, creates files | — |
| `bot` | dependency bumps by an account whose name matches `[bot]` | — |
| `vendor_import` | replaces `vendor/thirdparty/` wholesale | — |

**The planted effect.** Which files receive a fix after the snapshot is drawn from

```
P(file i is touched by a given fix) ∝ loc_i^a × exp(b · busyness_i) × exp(Σ_k β_k · z_k(i))
```

where `z_k` is the within-repo z-score of planted property k's **density** (so the effect is beyond size by
construction) and `β_k` comes from `--effect`, default 0 for every property. `a` and `b` are fixed constants
recorded in the manifest. With every β = 0 the repository is a **negative control**: fixes follow size and
busyness only. With `--effect branches=0.5` it is a **positive control** for that property.

**A planted change effect, separately.** `--effect d_branches=β` makes fix probability depend on the *change*
in a file's branch density over the year before the snapshot. To support it, the history must really change
those files' structure during that year (ordinary commits that add or remove branches), and the manifest
records each unit file's planted properties **at both points**. **[r2]** At least 40% of the unit files change
their branch density in that year, with the sign of the change independent of everything else; the manifest
records the share.

**Ordinary selection must not depend on the planted properties.** Only fixes do. State the mechanism in
`README.md` so a reviewer can check the negative control is truly null.

## The manifest

`manifest.json`, schema versioned, with: the arguments and seed; the generator's version; `a`, `b`, every β;
the snapshot and prior points; per file — path at the snapshot, path history through renames, `is_unit` and
why, every planted property at both points; per commit — hash, time, true type, the label convention used,
files touched, and for fixes which defect; and **the expected labels**: for each commit after the snapshot,
whether SA3's primary outcome rule should count it, derived from the written rule in
`docs/sa3_registration_consolidated.md` section 4, with the clause that decides it. Where the rule is
ambiguous for a generated case, do not decide: list the case under `ambiguous` with both readings.

**[r2]** Positive files are given as file ids with their **path at the snapshot**, and only for unit files
that exist at the snapshot: that is the set SA3 ranks. Unit files a commit touches that are not in that set
(created later) are listed separately, not as positives. The tree-wide rule is applied to the snapshot's unit
files. Two cases are ambiguous by ruling of the first review and are listed, not decided:

- a revert whose target was made after the snapshot but whose message quotes a ticket from the target's
  subject (readings: counted through the reference; not counted, it is a non-qualifying revert);
- every merge that brings in a linked commit. Four readings: the three in the first build, plus **"taint
  governs the control pool only"** — the merge is counted when it shares a file with the linked commit, even
  if it also brings in a fix-worded commit; that is what `tools/sa3_outcomes.py` does.

For C, the manifest also records the count of pointer declarations per file beside `pointer_ops`, and says
which of the two a keyword-family instrument is expected to see.

Also record the realised truth: for each unit file, the number of true fixes after the snapshot. That, not the
label, is what an ideal study would have as its outcome.

## Mutations

`--mutation NAME` produces the same repository with one thing changed, so the pipeline's response to a known
fault can be measured. Each is small, named, and tied to a real past fault in `docs/STUDY_DEFECT_LOG.md`:

| name | change | log entry it re-creates |
|---|---|---|
| `merge_workflow` | work arrives through merge commits; the fix reference is in the brought-in commit, not the merge | 4, 17 |
| `bot_merges` | every merge is authored by an account matching the bot pattern | 29 |
| `squash_merges` | the same work squashed, references kept in the squash message | 17 |
| `sweep_labelled_fix` | the licence sweep's message says "Fix" and names a ticket | 11 |
| `tickets_for_everything` | 60% of ordinary commits become `feature_with_ticket` | 30 |
| `reverts_of_new_code` | **[r2]** every revert in the outcome window targets a commit made after the snapshot, where one exists; the exceptions are listed | 16 |
| `vendored_half` | half the unit-looking files sit under an imported third-party directory | 29 |
| `test_fixtures` | a large directory of tiny generated test inputs in the main language | 29 |
| `mixed_language` | a second language holds 40% of the files | 1, 6 |
| `renames_after_snapshot` | 20% of files are renamed in the outcome window. **[r2]** These renames edit no other file: callers are not rewritten, and the manifest says their imports go stale | 39 |
| `no_references` | fixes carry keywords only | 3 |
| `huge_import_merge` | one merge brings in 500 commits | 17 |

Mutations compose. The manifest lists which were applied and what each changed in the truth.

**[r2]** Where a commit of the base history edits a file only because it calls a renamed or deleted file, the
manifest marks that edit as a caller edit, so "which files does non-fix work touch" can be checked against
the planted properties.

## Tests (part of the deliverable)

`tests/test_control_repo.py`, runnable with the repo's pytest, using `--profile small`:

1. Same arguments, same hashes; different seed, different hashes.
2. The repository is valid: `git fsck` clean, every commit in the manifest exists, every file path in the
   manifest exists at the snapshot.
3. Planted structure is real: for a sample of files, an independent count of branch keywords and lines in the
   file's text equals the manifest; for Python, the file compiles (`ast.parse`).
4. `tools/sa3_nesting.py` agrees with `max_nesting` on every generated file (run it with the tree-sitter
   Python named in its docstring; skip the test with a clear reason if that interpreter is absent).
5. The negative control is null **in the truth**: over 20 seeds, the rank correlation between a planted
   property's density and the count of true fixes, within size deciles, averages within ±0.03 of zero.
   **[r2]** Run at `--files 800` (60 files cannot resolve ±0.03); every planted property is tested; a mean
   passes if it is within three of its own standard errors of zero and within ±0.03.
6. The positive control is real: with `--effect branches=0.5` the same statistic is clearly positive, and the
   stronger the β the larger it is (three strengths).
7. Each mutation changes what it says and nothing else: diff the two manifests. **[r2]** Also compare which
   unit files each commit touches: `renames_after_snapshot` may add the renamed files and nothing else.
8. `sweep` commits touch at least half the unit files; `feature_with_ticket` commits never fix a defect.

## Rules for the builder

- Read `docs/sa3_registration_consolidated.md`, `docs/STUDY_DEFECT_LOG.md` and `tools/sa3_nesting.py`. Do not
  read study data, scans or outcome files; you do not need them and must not touch them.
- Do not run the engine or any study tool on real repositories. Phase 1 needs neither.
- Generated repositories go under `--out`; in tests, under pytest's temporary directory. Never inside the
  worktree, never under the study-data directory.
- Standard library plus what the repo's test environment already has. No new dependencies.
- Plain, readable code with docstrings. A reviewer will read all of it.
- When finished, report: what was built, the test results, every entry in `DECISIONS.md`, and anything in this
  spec you believe is wrong or impossible.
