# Parameters, branch logic and errors: the pattern, and what breaks it (exploratory, no hypotheses fixed beforehand)

**Status:** exploratory. Two data sets: (A) function-level structure of 4.17M non-test functions of 5+ lines in 14 languages in the v2.12.0 population database (`pop_outliers.py`, output `args_branch_population_output.txt`); (B) function-level fix outcomes in four C repositories, 969k function-quarters and 18.6k fix touches (`fix_args_branch.py`, outputs `args_branch_errors_output.txt` with 100 size bins, `..._deciles.txt` with 10). "Branch logic" is the engine's `complexity`, which is identical to its `struct_branch` count (rank correlation 1.00). "Errors" is read two ways: error-handling code (guards `def_safety`, early exits `state_bailout_hits`) in A, and fix commits in B.

## A. Structure: branch logic, parameters and error handling
1. **Branch logic is mostly size.** A model of log(1 + branches) on log(lines) explains 72% of the variance in C, 66% in C++, 63% in Go, 37% to 50% in most others (Dart 18%). **Adding the parameter count adds almost nothing**: 0 to +0.005 of explained variance in C, C++, Python, Go, Java, Kotlin; +0.002 to +0.017 in C#, Rust, TypeScript, JavaScript, Swift; +0.08 in Dart and PHP.
2. **The shape is an inverted U, and wide parameter lists mean flat bodies.** At the same size, average branch logic (log units relative to the size-only model): 0 parameters -0.17, 1 +0.04, 2 +0.07, 3 +0.05, 4 +0.01, 5 to 6 -0.04, 7 to 9 -0.13, 10 or more -0.29. The drop for wide functions is steep in Java (-0.87 at 10+), Go (-0.70), Python (-0.44) and shallow in C (-0.11). Constructors, factories and generated classes are wide and have no branches.
3. **Error-handling code grows with both.** Share of functions with a guard: 11% to 13% for flat functions with few parameters, 30% for branchy ones, up to **39% for branchy functions with 5 or more parameters** (parameter validation); early exits likewise (3.5% to 6% against 15%). Wide *and flat* functions guard less than their size predicts (13.6% against 21% expected).
4. **Outliers, and what they are.** Functions the size-and-parameters model gets most wrong (beyond 3.5 standard deviations), compared with other functions of the same size:
   - **Flatter than expected** (13,216, 0.32%): large straight-line code, mostly table and initialiser building, assembly and DSP and platform setup in operating-system sources (reactos 14%, freebsd 13%, linux 11%); name words `apis`, `intrinsifier`, `methods`, `board`, `dsp`, `asm`, `iunknown`. Guards 12% against 33% expected; early exits 3% against 11%.
   - **Narrow and knotty** (0 or 1 parameter, branches 40 or more; 13,192): compilers, parsers, scanners, state machines and GUI handlers (`dagcombiner`, `parser`, `scan`, `gui`, `editor`). Guards 39.5% against 33.4% expected, early exits 13.6% against 10.8%.
   - **Wide and flat** (6+ parameters, no branches, 10+ lines; 38,327): constructors and generated localisation code (`localization` x77, `cupertino` x54, `constructor`, `factory`, `init`).
   - **Branchier than expected** (2,865, 0.07%) is 66% one repository's test suite (dotnet `runtime`: names `funclet`, `sub`): not real logic.
   The outlier groups are concentrated: 47% to 90% of each group sits in ten repositories, so they are mostly the character of particular code bases (operating systems, compilers, generated code, test suites), not scattered individual functions.

## B. Errors: where fixes land (four C repositories)
Unit: a function in a quarterly snapshot (source, 5+ lines). Outcome: a fix commit of the crucible's v3c events touched it in the next quarter (function from the git hunk header, joined to the snapshot by path and name; 46% (libgit2) to 78% (curl) of hunks could be placed). Reported as observed over expected from size alone (repository by 100 size bins), 95% interval over intervals.
1. **Fix rate falls with parameter count at the same size.** All fixes: 0 parameters **1.55**, 1 parameter 1.09, 2 0.96, 3 to 4 0.95, 5 or more **0.89**. Wide functions are not where fixes land; the clearest signal is the other end.
2. **Zero-parameter functions are fixed most**: 1.55 times the size-expected rate; 1.79 [1.49, 2.10] for flat ones; for regression-class fixes 2.08 times, and **3.16 [1.56, 5.14] for zero-parameter branchy functions** (46 fixes). A function with no parameters reads hidden state (globals, `f(void)`); this is a reading of the pattern, not tested.
3. **Branch logic adds nothing beyond size.** With 10 size bins branchy functions looked 12% more fix-prone; with 100 bins the effect disappears (rank within size: flat 1.07, branchy 0.97). A coarse size control had made a size effect look like a branch effect.
4. **The two-way pattern is additive.** Each cell of parameters by branch rank is within about 10% of the product of its two margins for all fixes; the largest departures are flat zero-parameter functions (+8%) and flat 5-plus-parameter functions (-12%).
5. **Types of fix differ.** Regression-class fixes rise at the wide and branchy corner (1.26 [1.01, 1.55] at 5+ parameters and top branch rank) and at zero parameters; **other-fix** (cause not found in history) are *lower* in wide functions (0.86) and show no corner effect.
6. **Outlier functions.** Of 4,867 long-lived functions (8+ quarters, expected 1+ touch), 170 (3.5%) were touched 3 or more standard errors more than expected and only 4 fewer. The over-fixed are the central orchestrators (redis `processCommand` 24 against 6.2 expected, `genRedisInfoString` 28 against 7.7; libxml2 `parseAndPrintFile` 32 against 8.0, `xmlParseTryOrFinish` 28 against 8.0; curl `create_conn`, `multi_runsingle`) and a set of small or platform-dependent ones (redis `sigsegvHandler` 15 against 2.1, `restoreCommand`, `freeClient`; curl `my_getaddrinfo` 11 against 1.8, `Curl_if2ip` 11 against 1.9 in 18 lines with 6 parameters and no branches; redis `setGenericCommand` with 9 parameters, 11 against 1.4). **Parameters do not identify them**: 13% of the over-fixed have 5 or more parameters, against 15% of all long-lived functions.
7. **Big, branchy and never fixed (25 of 368) break the pattern for a reason other than design.** They are vendored or stable third-party code (redis `luaV_execute`, `lzf_compress`, `malloc_conf_init`) and macros the parser reads as functions (libxml2 `TRIO_ARGS3` to `TRIO_ARGS6`), which the projects' fixes do not touch.

## What can be said
- Branches follow size; parameters add little to it. Wide parameter lists belong to flat code, and wide *and* branchy functions carry the most error-handling guards.
- At the same size, functions are **not** more fix-prone for having more parameters or more branches. The notable group is the opposite end: functions with **no** parameters, and for regression-class fixes the zero-parameter branchy functions.
- The functions that break the pattern are mostly large central or platform-dependent code that attracts fixes, and vendored code and parser artefacts that attract none. Structure (parameters, branches) does not pick the first group out.

## Caveats
Function attribution by hunk-header name is approximate (a quarter of hunks unplaced in libgit2; names that changed between snapshot and fix are lost). "Touched by a fix" is not "caused a defect"; classes come from commit text. Expected rates use size alone, so any factor correlated with size and unmeasured (file, author, age) is not controlled; the outlier list shows this: it is the largest and oldest functions. Four C repositories only for B; A pools 14 languages with very different styles, and its outlier groups are dominated by a few large code bases. Exploratory and unregistered; ten or more comparisons were read.
