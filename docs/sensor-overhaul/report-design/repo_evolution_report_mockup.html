Repo evolution report · mock-up

DPDK: ten years of change, by kind

How the repository grew, where the work went, how quickly and where repairs arrived, and which functions keep needing them.

Mock-up with real numbers from our DPDK scans (41 quarterly snapshots) and git history. The Mesa comparison row is also measured. Everything under "Not drawn yet" is a proposal from the design guide, not a result.

At a glance

Strong · rule-based counts

Where the function edits went, whole history

Function edits are the functions named in each commit's diff headers (a function edited in two commits counts twice). A sweep is a commit that edits more than 60 functions. Fixes are commits with a Fixes: trailer or a fix-like subject.

So whatAbout one edit in five is a planned mechanical sweep that says little about the project's own health; separating it out makes every other trend readable.

1 · Growth

Strong · from the scans

T1How big the code base is

Functions found by the scan at each quarter. Dots mark quarters with a sweep over 1,000 functions.

T2What the growth is made of

Above zero: new functions. Below: functions that disappeared. "Moved" means the same name reappears in another file, so most of it is reorganisation, not creation or loss.

T3Age layers of the code base

Functions present at each quarter, grouped by the year they first appeared. "2016" includes everything that existed at the first scan.

So whatGrowth is mostly new code arriving in new files (drivers). Few functions are deleted with a whole file; about a third of apparent deletion is code that moved.

3 · Sweeps

Strong · rule: over 60 functions in one commit

Planned mechanical work: renames, API conversions, reformatting, namespace changes. These are the largest commits by function count.

DateFunctionsSubjectLater cited as the cause of a fix
So whatEach sweep is a migration with a known scope. Whether repairs followed is visible per sweep, so a team can see which kinds of sweep were quiet and which were not.

4 · Repairs: when, and how close

Moderate · causes named by Fixes: trailers

T7How long fixes took

How much closer than chance fixes land

Within one or two calls of a changed function, against same-sized functions in the same file. 1.0 (the line) means no pattern. Callers (code that depends on the changed function) are enriched more than callees.

Day 1 function B changes.
Month 8 a bug appears; the fix edits B itself about half the time.
When it does not, the fixed function is within two calls of B about 1.45 times as often as a random neighbour in the same file, usually one of B's callers.

Cause type is the first verb of the causing commit's subject. A fix of a fix is the tightest; a feature is followed by scattered, later repairs.

So whatAfter a feature, repairs arrive late and scattered: widen the review. After a fix or an optimisation they come back to the same function: look there first.

6 · Which changes get repaired

Strong · size is the one per-change signal that held up

Share of changes later cited as the cause of a fix, by size

Organic commits from 2015 that are at least three years old (so every change had time to be repaired). Size is the number of functions the commit edits.

So whatBigger changes are repaired far more often. Nothing else we measured (author experience, reviewer trailers, structure) added to size.

7 · What this history can and cannot tell you

Moderate · tested on this repository

Detection regime Slow

The causing change is, at the median, the 1,504th most recent change before the fix. Bugs here are found over months, not days, so structure helps more than recency.

Look-first list 79% top 20

Given a repaired function, the neighbourhood ranking put the true causing commit in its top 20 for 79% of tested repairs. Most-recent-first managed 2.3%; file overlap 61%.

Bisect saving 6.4 vs 14.7 tests

Weighting a bisect by that ranking needed 6.4 tests on average against 14.7 for plain bisect (DPDK and Mesa pooled).

Shipped bugs Cc: stable

Fixes tagged Cc: stable took a median 371 days; untagged fixes took 20. The tag marks bugs that reached a release.

Label quality Good

27.5% of all commits (36% of the commits that change functions) carry a Fixes: trailer. 83% of unnamed fix-like commits had a cause found by blame. The subject rule misses about 8% of fixes in the remainder.

Cannot say

Whether a particular change will need a fix (size predicts, little else does). Fixes with no findable cause are shown as such, not as "extrinsic".

So whatTreat the look-first list as a shortlist that narrows a search about twenty-fold, right about four times in five here. It is not a verdict on any one change.
