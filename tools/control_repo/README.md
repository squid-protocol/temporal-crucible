# Control repository generator

A generator of synthetic git repositories whose truth is planted and written down, so that the SA3 study
pipeline can be run on something with a known answer: a **negative control** (no structural effect at all) and
**positive controls** (a known effect of a known size). Built to `docs/process/control_repo_spec.md`, phase 1.
Every choice that spec did not make is in `DECISIONS.md`.

## Use

```
python tools/control_repo/generate.py --out DIR --seed N [--language python|c] [--files 400]
        [--effect NAME=BETA ...] [--mutation NAME ...] [--years 4] [--profile small|default]
python tools/control_repo/generate.py --list-mutations
```

- `DIR/repo/` is an ordinary git repository (full, not bare, branch `main`, working tree checked out).
- `DIR/manifest.json` is the truth.
- The same arguments always give the same commit hashes. Nothing about the machine (git identity, time zone,
  configuration, clock) gets in; no network is used and no other repository is read.
- `--profile small` (about 60 files, 300 commits) takes well under a second; `default` (400 files, 3000
  commits) about 3 seconds. `--out` must be outside this repository.

Effect names: `branches`, `max_nesting`, `calls_in`, `calls_out`, `state_writes_in_branches`, `d_branches`
(the change in branch density over the year before the snapshot), and for C also `pointer_ops`, `alloc_ops`.
With no `--effect` the repository is a negative control. `--effect branches=0.5` makes it a positive control
for branch density.

## What is in the repository

- `src/`: the **unit files**, in directories of uneven size two or three levels deep. Each is generated code
  that parses (Python: `ast.parse`; C: `gcc -fsyntax-only`) with functions, calls into other files,
  conditionals, loops and assignments. Sizes are heavy-tailed with exact ties.
- Files a correct study must not rank, each marked in the manifest with `is_unit: false` and the reason: test
  files (`tests/`), imported code (`vendor/thirdparty/`, marked `linguist-vendored` in `.gitattributes`),
  documentation (`docs/`, `README.md`), one generated file (its first line says "Code generated by ..."), an
  `export-ignore` directory of real-looking source (`src/<top>/experimental/`, absent from `git archive`), the
  licence, `.gitattributes` and a dependency list.
- A first-parent history over `--years` (default 4) in which every commit has a true type: `ordinary`, `fix`
  (written in one of six conventions, from "Fixes #N" to no signal at all), `feature_with_ticket` ("Fixed #N --
  Added ...": looks like a fix, is not), `revert`, `sweep` (licence header, reformat; some say "Fix lint"),
  `rename`, `delete`, `add`, `bot` (dependabot[bot]) and `vendor_import`.

## What the manifest says

- The arguments, generator version, schema version, the constants `a` and `b`, and every beta.
- The **snapshot** (the commit at 80% of the history) and the **prior point** (the last commit at least 365
  days before it): hash and time.
- Per file: its id, kind, `is_unit` and why, its path at the prior point, at the snapshot and at the end, its
  path history through renames, its drawn densities, its busyness, and every planted property **at both
  points**: `loc`, `branches`, `max_nesting`, `calls_in`, `calls_out`, `state_writes_in_branches` (C also
  `pointer_ops`, `alloc_ops`), each with its density. `branch_mapping` says which keywords `branches` counts;
  `risk_operations` says whether pointer and allocation operations were planted (C) or not (Python).
- For C, beside `pointer_ops` (dereference writes), `pointer_declarations` (`long *data` parameters and the
  `long *cursor` / `long *buf` locals); `pointer_mapping` says which an instrument is expected to see.
- `stale_imports` on a Python file whose import of a file moved by `renames_after_snapshot` was left as it was.
- `change_in_prior_year`: how many unit files changed branch density in the year before the snapshot (at least
  40% by design), and how many went up.
- Per unit file, the **realised truth**: `true_fixes_after_snapshot` (and within the 730-day window). That,
  not any label, is what an ideal study would have as its outcome. Also its fix weight and z-scores.
- Per logical commit: hash, time, true type, label convention, author, message, files touched, and for fixes
  the defect id and files; for reverts the target and whether it is before the snapshot; and
  `caller_edit_ids`, the files a rename or delete edited only because they call the moved or deleted file.
- `realised`: the commits as delivered (direct, merge, a merge's branch commits, squash).
- `expected_labels`: for every commit after the snapshot, whether SA3's primary outcome rule (HP, section 4 of
  `docs/sa3_registration_consolidated.md`) should count it, with the clause that decides it, and its
  `positives`: the snapshot's unit files it touches, as ids with their **path at the snapshot** (the set SA3
  ranks). Unit files created after the snapshot are listed apart (`touched_unit_files_not_at_snapshot`). Where
  the written rule can be read more than one way, `counted` is `null` and the case is listed under `ambiguous`
  with every reading. **Merges are decided** by the owner ruling of 2026-11-14 (top-level `rulings`): tainted
  merges follow SA3's code, so a merge counts when its first-parent diff shares a file with a brought-in, non-bot
  linked commit, a fix-worded companion notwithstanding; over the 50-commit cap or tree-wide it does not. The
  other merge readings stay on the label as `unruled_readings`. What is still open is a revert of post-snapshot
  code that quotes a ticket (two readings, DECISIONS.md 45), in a merge or not.
- `mutations`: which were applied, what each changes in the truth, and counts of what it changed.

## Why the negative control is null (the mechanism to check)

Only one thing in the generator ever looks at a planted property: the choice of which files a **fix after the
snapshot** touches, which uses

```
weight_i = loc_i^a * exp(b * busyness_i) * exp(sum_k beta_k * z_k(i))
```

with `loc` at the snapshot, `a = 0.6`, `b = 1.0`, and `z_k` the within-repo z-score of property k's density at
the snapshot (`history.Simulator.compute_fix_weights`). With every beta at 0 that is `loc^a * exp(b * busyness)`.
Everything else is blind to the planted properties by construction:

- Densities are drawn per file from the file's own random stream, independently of its size and its busyness,
  which come from other streams.
- **Ordinary commits** (and ticket features) pick files with weight `planned_loc^0.6 * exp(busyness)`
  (`history.Simulator.ordinary_weights`), where `planned_loc` is the size drawn before any structure exists.
  Not even a file's realised length, which can grow when dense structure does not fit, reaches it.
- Fixes before the snapshot use `loc^a * exp(b * busyness)` with every beta 0.
- Reverts, sweeps, renames, deletes and bot commits choose uniformly or by fixed rules.
- Edits change integer literals only. The one exception is the branch change in the year before the snapshot
  that `d_branches` needs: each file is scheduled to change with probability 0.9, with a fair-coin sign, into
  ordinary commits of that year drawn uniformly, all from the file's own stream
  (`history.Simulator.start_churn_window`). The schedule never looks at structure, size or busyness, so the
  extra activity it adds is blind to the planted properties too.
- Renames and deletes edit their callers (Python imports, dropped calls); those edits are marked
  `caller_edit_ids`, so "which files does non-fix work touch" can be checked against the planted properties.
- Every random draw has its own named stream, so an effect cannot shift any draw before the snapshot: with and
  without `--effect` the history up to the snapshot is byte-identical (a test checks the hashes).

So with every beta at 0, the number of true fixes a file receives depends on its size and busyness only.

## GitHub Linguist's lists

SA3's universe rule (`tools/laws_units.py`) drops any path GitHub Linguist's `vendor.yml` or
`documentation.yml` matches. The base repository therefore uses no such name except where it plants a non-unit
on purpose (`vendor/thirdparty/`, `docs/`, `LICENSE`, `README.md`, `.gitattributes`). The names to avoid, with the
pattern each matches, are a fixed list in `codegen.LINGUIST_AVOID`; the generator checks the base layout against
it and never reads the lists. A test checks every unit path against the cached lists themselves
(`~/.cache/temporal-crucible/linguist-e0c78d62c42a/`) and skips, saying so, if they are absent. Two mutations
match the lists on purpose: `test_fixtures` (`tests/fixtures/`, test inputs) and `generic_dir_names`
(first-party code a Linguist-based rule wrongly drops).

## Fix conventions and SA3's link patterns

Fixes are written in seven conventions: "Fixes #N" (issue), a `Fixes: <hash>` trailer, a CVE id, "Fixes PROJ-N:
..." (`jira_fixword`), "PROJ-N: ..." (`jira_bare`), a bare keyword, and none (silent). The test file checks that
exactly the counted ones (and "Fixed #N -- Added ...") match the patterns of `tools/hist_meta.py` under
`--sa3-links`. A bare key is not counted, as SA3's code reads it; the registration's looser wording is kept on
the label as an unruled alternative (`unruled_readings`, reading `registration_wording`).

## For phase 2

- `--years 4` leaves about 270 days after the snapshot, less than SA3's 730-day window, and `--profile small`
  is below SA3's floors. A pipeline run needs the default profile (or more files) and `--years 10`.
- The manifest's snapshot is commit ceil(0.8 n) - 1 of the base timeline; SA3 picks its own. Either hand the
  snapshot to the pipeline or treat its choice as one of the things tested.
- **Density and size inside a band.** Counts are whole numbers, so among files of one size band with the same
  count, density falls as loc rises: inside size deciles density is rank-related to loc (about -0.04 to -0.10),
  although the planted densities are not. Fix probability rises with loc (loc^a), so a band-based statistic
  reads slightly negative even on the negative control (in C about -0.01 to -0.02 in some seed sets). Score a
  pipeline against the manifest's truth pushed through the same statistic, not against exactly zero.
- Imported code (`vendored_half`, `mixed_language`) receives no commits after the initial import.
- The licence sweep of `sweep_labelled_fix` says "Fix licence headers (#N)": a ticket with no fix word right
  before it, which SA3's code does not count (only "fix #N" is a fix reference there). The manifest's label is
  "not counted" anyway, because the sweep is tree-wide; it would differ only in a repository with under 20 unit
  files.

## Mutations

`--mutation NAME` (repeatable; they compose) gives the same repository with one thing changed, each re-creating
a fault in `docs/STUDY_DEFECT_LOG.md`. `--list-mutations` prints them:

| name | change | log |
|---|---|---|
| `merge_workflow` | work arrives through merge commits; the fix reference is in the brought-in commit | 4, 17 |
| `bot_merges` | every merge is authored by a `[bot]` account (implies `merge_workflow`) | 29 |
| `squash_merges` | the same work squashed, references kept in the squash message | 17 |
| `sweep_labelled_fix` | the licence sweep's message says "Fix" and names a ticket | 11 |
| `tickets_for_everything` | 60% of ordinary commits become `feature_with_ticket` | 30 |
| `reverts_of_new_code` | every revert in the outcome window targets a commit made after the snapshot, where one exists; the exceptions are listed | 16 |
| `vendored_half` | half the unit-looking files are imported code under `src/contrib/`, unmarked | 29 |
| `test_fixtures` | a large directory of tiny generated test inputs in the main language | 29 |
| `mixed_language` | a second language holds 40% of the files | 1, 6 |
| `renames_after_snapshot` | 20% of the snapshot's unit files are renamed in the outcome window; the renames edit no other file, so callers' imports go stale (listed) | 39 |
| `no_references` | fixes carry keywords only | 3 |
| `huge_import_merge` | one merge brings in 500 commits | 17 |
| `generic_dir_names` | 20% of the unit files sit under `cache/`, `dist/`, `extern/` or `env/`, names GitHub Linguist's vendored list matches by name alone; they stay units, with a note | 55 |

## Files

- `generate.py`: the CLI; writes the repository with one `git fast-import` and the manifest.
- `codegen.py`: a source file as a small model (functions of statements and control nodes), rendered to Python
  or C; every planted property is measured from the model the text is rendered from.
- `history.py`: the layout, the commit timeline and the simulation that edits the files.
- `mutations.py`: the named variants.
- `manifest.py`: the manifest, including the expected-label derivation.

## Tests

```
python3 -m pytest tests/test_control_repo.py
```

Repositories go under pytest's temporary directory. Test 4 needs an interpreter with
`tree_sitter_language_pack==1.20.0` (the version `tools/sa3_nesting.py` pins): the one running pytest, or the
one named by `CONTROL_REPO_TS_PYTHON`; without one it skips and says so. The two 20-seed statistics tests take
most of the time (they use two worker processes); the full run takes about two minutes on the development
machine. Test 5 passes a property if its 20-seed mean is within three of its own standard errors and within
0.03.
