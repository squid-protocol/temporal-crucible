# Control repository: decisions the spec left open

`docs/process/control_repo_spec.md` ("phase 1") is the brief. Every choice below is one it did not make. Numbers
are the code's constants; where a choice has a measured consequence, the measurement is given.

## Determinism and git

1. **Random streams.** Every random draw comes from `random.Random("<seed>:<purpose>:<entity>")` (history.stream):
   one stream per file for its size, busyness and structure, one per logical commit and purpose (file
   selection, non-unit touches, fix targets, wording, author), one per mutation. A change to one thing (an
   effect, a mutation) cannot shift any other draw. String seeding is stable across processes and
   PYTHONHASHSEED; no set is ever iterated. Test 1 runs the generator twice with different PYTHONHASHSEED, TZ
   and an inherited GIT_AUTHOR_NAME and gets byte-identical manifests and identical hashes. Not tested: a
   different platform. Selection weights use `math.exp`, so a libm that rounds differently could in principle
   change a weighted draw; the hashes are guaranteed for the same Python and C library.
2. **Git writing.** One `git fast-import` process writes every commit. Parents are given by mark (fast-import
   cannot read back a commit by hash before it finishes); each commit's hash is read back immediately with
   `get-mark`, so a later message can name it. After the import: `git reset --hard main` (the working tree is
   checked out), the temporary branch ref is deleted, and every recorded parent list is checked against
   `git rev-list --parents`.
3. **Environment of every git call** (generate.git_env): only PATH is inherited; HOME and XDG_CONFIG_HOME point
   at a private temporary directory, GIT_CONFIG_NOSYSTEM=1, GIT_CONFIG_GLOBAL inside that HOME, TZ=UTC,
   LC_ALL=C, GIT_NO_LAZY_FETCH=1, GIT_CEILING_DIRECTORIES = the parent of `DIR/repo` (git can never discover a
   repository above the generated one), `-c gc.auto=0 -c maintenance.auto=false` on every call, and
   `gc.auto=0` is also written into the generated repo's config. Author, committer and date of every commit
   are explicit in the fast-import stream (`+0000`). The default branch is `main`; every file is mode 100644.
4. **Safety guards.** `generate.py` refuses an `--out` inside the repository that holds the generator, and
   refuses to write into a non-empty `DIR/repo`.
5. **The manifest is deterministic too:** no wall-clock time or machine path is written into it.

## Size of things

6. **Profiles.** `small`: 60 files, 5 commits per file (300). `default`: 400 files, 7.5 per file (3000).
   `--files N` overrides the file count and the commit count scales with it. `--profile small` generates in
   about 0.2 s; `default` in about 3 s.
7. **Layout shares** of `--files`: docs 5%, tests 12%, vendored 6%, export-ignored 2%, five fixed files
   (LICENSE, .gitattributes, README.md, the dependency list, the generated table), unit files the rest (at least
   20), plus about 1.2% of the commit count as unit files added later. Unit directories: about one per nine
   unit files, 2 or 3 levels under `src/` (`src/<top>/<dir>[/<dir>]`), file counts Zipf-weighted (exponent 1.2)
   so a few are big and many small. At seed 1 the default profile's directories under `src/` hold 84, 41, 26, ...,
   1, 1 files.
8. **What is not a unit, and why** (`is_unit` and `unit_reason` per file): tests (under `tests/`); vendored
   (`vendor/thirdparty/`, marked `linguist-vendored`); documentation (`docs/`, README.md); the generated table
   (header "Code generated by tablegen ... DO NOT EDIT.", placed in a unit directory so only its header gives
   it away); LICENSE; .gitattributes; the dependency list; and the **export-ignored** directory
   (`src/<top>/experimental/`, real source code in the repo's language). Section 3 does not name export-ignore;
   these files are not units because they are absent from `git archive` of the snapshot, which the universe and
   the scan are built from (test: `git archive` really omits them).
9. **Sizes.** Planned unit sizes are lognormal (median 70 lines, sigma 0.95), clipped to [12, 3000]; 15% copy
   another file's planned size exactly, so there are exact ties. Non-unit code files: median 60 (tests 36),
   sigma 0.8, [12, 1500]. A file is generated to its planned size exactly unless its planted structure does not
   fit, in which case it is the smallest size that holds it. Measured over five default-profile seeds: 2.7% of
   Python and 6.4% of C unit files exceed their planned size (mostly files planned under 30 lines). The
   manifest records the planned size (`planned_loc_target`) and the real line count at both points.

## Planted structure

10. **Densities** (per line; drawn independently of size and of each other, from the file's own stream):
    branches lognormal median 0.075 (Python, truncated to [0.01, 0.20]) or 0.06 (C, [0.01, 0.12]: C spends more
    lines per branch); cross-file calls out 0.025 [0.002, 0.10]; state writes in branches 0.02 [0.002, 0.08];
    C pointer writes 0.02 [0.002, 0.08]; C allocation calls 0.012 [0.002, 0.06]. Count = round(loc x density).
    `max_nesting` is planted as 1 + floor(Exp(rate 0.65)), at most 7 and at most the branch count. `calls_in` is
    planted as an attractiveness (lognormal, sigma 0.7): a new call site picks its callee file with weight
    planned loc x attractiveness. The manifest records the drawn densities (`planted_density`) and the realised
    density (count / loc) at both points.
11. **What a "density" is for each property** (used for z-scores and for tests 5 and 6): count / loc for
    branches, calls_in, calls_out, state_writes_in_branches, pointer_ops, alloc_ops; for `max_nesting`, which is
    a depth, not a count, the depth itself; for `d_branches`, branch density at the snapshot minus at the prior
    point (0 for a file absent at the prior point).
12. **Branch mapping** (manifest `branch_mapping`): Python counts the keywords `if`, `elif`, `for`, `while`; C
    counts `if`, `for`, `while`, `switch` (an `else if` carries one `if`). `else`, `try`/`except`, `case` and
    `default` are not branches. No branch keyword appears anywhere else in a file: no comprehensions, ternaries,
    `do` loops, or keywords in comments, strings or identifiers.
13. **Nesting** follows `tools/sa3_nesting.py`: control nodes are Python if/for/while/try (a `try` is a control
    node but not a branch), C if/for/while/switch; an `elif` / `else if` link sits at its chain's depth; an `if`
    inside an `else:` block or braced `else { }` is one deeper. Python `try` blocks are added only inside
    existing depth, so they never raise `max_nesting`.
14. **Calls.** Only unit files make cross-file calls, and only to unit files. `calls_out` = call sites in the
    file whose callee is defined in another file; `calls_in` = call sites in other files whose callee is in
    this file. Python imports each callee (`from src.a.b import name`); C declares it `extern`. Every C file
    has prototypes for its own functions. Generated Python modules may import each other in a cycle: the text
    parses (and C compiles with `gcc -std=c11 -fsyntax-only`), but the code is not meant to be run.
15. **State writes in branches** = assignments to file-level state (`_STATE[...] = ...` in Python,
    `g_state[k] = ...;` in C) lexically inside an arm of an `if` (any arm, `elif`/`else` included) or a C
    `switch` case, at any depth. A loop body alone is not a conditional. Unconditional state writes also exist
    (0.6% of lines) and are not counted.
16. **C risk operations:** `pointer_ops` = dereference writes `*cursor = ...;`; `alloc_ops` = calls to `malloc`
    and `free` (they come in pairs, so the count is even). Python files have neither, and the manifest says so
    (`risk_operations`).

## The history

17. **Commit mix** (shares of the commit count): fix 20%, feature_with_ticket 5%, bot 4%, revert 1.5% (at least
    one on each side of the snapshot, none in the first six commits), add 1.2%, rename 0.8%, delete 0.6%,
    vendor_import 1 (3 at 1000+ commits), sweeps at fixed positions (small: reformat "Apply code formatter" at
    35%, licence "Add SPDX licence headers" at 86%, reformat "Fix lint" at 93%; default adds "Fix lint
    warnings" at 60%), ordinary the rest. The first commit is the initial import (type `add`).
18. **Times.** From 2020-01-01T00:00:00Z over `--years` x 365.25 days, exponential gaps, at least 60 s apart.
19. **Snapshot** = the logical commit at index ceil(0.8 n) - 1 of the base timeline (before any mutation adds
    commits), as delivered on the first-parent chain (a merge or squash closes at it). **Prior point** = the last
    first-parent commit at or before snapshot time - 365 days; if `--years` is too short it is clamped to the
    first commit and the manifest says `clamped_to_first_commit: true`.
20. **Ordinary commits** pick 1 to 10 unit files (1 + a geometric count, continuation probability 0.45, at most
    10) by weighted sampling without replacement with weight `planned_loc ** 0.6 * exp(1.0 * busyness)`. The
    planned size, not the current line count, is used so that no density can reach the selection even through a
    file's realised length (see 9). Busyness is a standard normal per file, from its own stream. An edit changes
    one or two integer literals: no lines, no structure. 30% of ordinary commits also edit a test file and 8% a
    docs file, only while the commit stays within 10 files. In the year before the snapshot an ordinary commit
    also carries the files scheduled into it for a structural change (21, revised in r2); they take slots out of
    the 10, and the busyness draw fills the rest.
21. **The year before the snapshot** (revised in r2, see 47). Each unit file alive when the year starts is, from
    its own stream and nothing else, scheduled to change with probability 0.9 (`history.CHURN_SHARE`), given a
    fair-coin sign, and placed into 1 + floor(Exp(mean 1.5)) ordinary commits of that year drawn uniformly. Each
    scheduled touch applies max(1, round(0.1 x branches)) steps; the total is capped, for both signs alike, by
    the branch units the file could remove at the start (`codegen.removable_units`), so a file with none does
    not change. +1 adds an `elif` arm or a leaf `if` holding a filler statement; -1 removes an `elif` arm of
    filler statements, or flattens a leaf `for` / `while` / `if` / `switch` into its parent (its statements stay,
    so calls and pointer and allocation operations stay; an `if` or `switch` is flattened only if no state write
    would leave a conditional; flattening an `if` with `elif` arms removes all its branches at once). A step never changes max nesting or state writes in branches; calls change in that year only
    through deletes. Only these steps change structure. The manifest records the realised share
    (`change_in_prior_year`).
22. **Fixes.** A fix touches 1, 2 or 3 files (probabilities 0.7, 0.2, 0.1), drawn by weighted sampling without
    replacement. After the snapshot the weight is exactly the spec's formula with `a = 0.6`, `b = 1.0`, `loc`
    = the line count at the snapshot, and `z_k` = the z-score (population SD; 0 if the property is constant) of
    density k over the unit files at the snapshot; the per-file weight and z-scores are in the manifest. Before
    the snapshot every beta is 0 and `loc` is the current line count, so an effect cannot alter anything up to
    the snapshot (tested: identical hashes up to the snapshot with and without effects). Files added after the
    snapshot are never fixed. A fix changes a literal inside a conditional in each defect file; 35% also edit a
    test file. Each fix has its own defect id.
23. **Fix conventions** (per commit, recorded as `convention`): `issue` "Fixes #N" in the body 30%; `trailer`
    "Fixes: <12-hex hash> ("subject")" naming the last commit that edited the first defect file 10%; `cve` 8%;
    `jira_fixword` "Fixes PROJ-N: ..." 6% and `jira_bare` "PROJ-N: ..." 6% (r4, see 57); `keyword`
    "fix crash in ..." 25%; `silent` 15%.
24. **Reverts** target an earlier ordinary or feature_with_ticket commit that changed no structure and is not yet
    reverted (70%: one of the 30 most recent; otherwise any), and put back the literal values it changed that
    still differ. The message is git's: `Revert "<subject>"` + "This reverts commit <hash>." A revert of a ticket
    feature therefore quotes "Fixed #N" (signal `quoted_fixref`): if its target qualifies the revert counts
    anyway; if not, the case is ambiguous (45). If nothing is revertable the commit becomes ordinary
    (`notes.revert_fallback`).
25. **Sweeps** touch 85% of unit files and half the test files: the licence sweep adds two header lines; a
    reformat flips quote / comment style without changing lines or structure.
26. **Renames** of the base history move a unit file to another directory (70%) or prefix its name (30%); Python
    callers' import lines change in the same commit. **Deletes** remove a unit file; calls into it become local
    statements in the same commit. Either way the callers are listed per commit as `caller_edit_ids` (r2): they
    were edited only because they call the moved or deleted file. **Bot** commits ("dependabot[bot]") bump one
    line of the dependency list. **Vendor imports** regenerate every file under `vendor/thirdparty/`.

## Expected labels (SA3 section 4)

27. Labels are derived from the signals the generator itself put into each message, never by parsing text, for
    every commit after the snapshot (branch commits of a merge included). Each names the deciding clause, quoted
    from section 4 (or section 2 for the window and the first-parent unit). Every applicable exclusion is
    listed (window, tree-wide, over the 50-commit cap), not just the first.
28. Decided cases: a fix reference, CVE id, Jira key or `Fixes:` trailer counts; a keyword-only or silent fix does
    not (keyword wording is the KW tier); a feature_with_ticket counts (it carries "#N"); a revert counts if its
    target is a commit at or before the snapshot commit, otherwise not (HP_allreverts would), unless it quotes a
    ticket (45); branch commits of a merge are not units; a bot-authored merge is treated like any other merge
    (section 4 bars inheritance *from* a bot's commit, not *by* a bot-authored merge), so `bot_merges` has
    exactly `merge_workflow`'s labels.
29. **Merge readings** (revised in r2, see 46; since r3 the ruled one decides, see 52). Section 4 says a merge
    inherits a link from a commit it brings in, and also that a merge "bringing in a linked or fix-worded commit"
    is tainted and in no outcome. Four readings are computed for every first-parent merge: `inherit` (taint =
    bringing in a fix-worded commit or a link the merge may not inherit: a bot's, or a revert of a commit brought
    in by the same merge), `nonqualifying_revert_taints` (also tainted by a brought-in revert that does not
    qualify), `literal_taint` (never counts), and `taint_governs_control_pool_only` (46). Under every reading
    that can count, a merge counts only if its first-parent diff shares a file with an inheritable linked commit,
    and its positives are the snapshot unit files in that intersection. When all readings agree the label is
    decided; otherwise the case is ambiguous with every reading's outcome, clause and positives.

## Mutations

30. `bot_merges` implies `merge_workflow` (without merges it would change nothing). `squash_merges` cannot be
    combined with either (both decide how work reaches main); the CLI refuses the combination.
31. **Grouping** for merges and squashes: groups of 1-4 consecutive commits (weights 0.35, 0.30, 0.20, 0.15),
    never crossing the snapshot or prior point. Merge commits are `--no-ff` merges of a branch made from the
    current main, titled "Merge branch 'topic-N'" with no "#N" (a PR number would itself be a fix reference under
    HP). Squash: bot commits stay direct; a group closes before a commit that names a member (revert or
    trailer); the message is the first subject plus every message as a bullet, so every reference is kept; the
    author is the group's first author. Merge and squash commits are dated one second after their last commit.
32. `vendored_half`: as many imported files as there are initial unit files are added under
    `src/contrib/<lib>/`, so half the unit-looking files are imported code; no `.gitattributes` line marks them
    (that is the fault), and `is_unit` is false. The units themselves are unchanged.
33. `test_fixtures`: 1.5 x the initial unit count of 2-5 line files under `tests/fixtures/generated/` in the main
    language. `mixed_language`: the other language (C for a Python repo, Python for a C repo) makes 40% of the
    files at the initial import, in `native/` or `scripts/` subdirectories of unit directories.
34. `renames_after_snapshot`: round(0.2 x unit files at the snapshot) rename commits inserted at random points
    after the snapshot, each moving a not-yet-moved snapshot unit file to another directory. (r2) Each edits only
    the moved file: no caller is rewritten, so a Python caller keeps importing the old path. The manifest lists
    this per caller (`files[].stale_imports`: callee id -> the path still imported) and per rename commit
    (`notes.stale_imports`). A later base-history rename of the same file rewrites its callers, as in the base.
35. `reverts_of_new_code` (wording per spec r2): every revert in the outcome window targets a commit made after
    the snapshot, where one exists. A revert right after the snapshot may find nothing revertable yet: it keeps
    a pre-snapshot target and is listed in `mutations.changed.reverts_of_new_code.kept_pre_snapshot_target`.
    Reverts before the snapshot are unchanged.
36. `huge_import_merge`: 500 consecutive post-snapshot commits delivered by one merge. When the window holds fewer
    (the small profile always does), all of them plus filler commits (type `add`, one new note file under
    `docs/imported/` each) at random times in the window make up the 500.
37. `tickets_for_everything` and `no_references` apply to the whole history, not only the window.
38. Every mutation's manifest entry has a `truth` sentence (what it changes in the truth) and `changed` counts.
    No mutation changes any planted property or true fix count.

## Tests

39. **Tests 5 and 6 use `--profile small` with `--files 800`** (spec r2), and two worker processes. At 60
    files the SE of a 20-seed mean is about 0.05, so "within +-0.03" cannot be resolved; at 800 files it is
    0.006-0.013. (r2) A property passes if its mean is within three of its own SEs of zero **and** within 0.03.
    The seeds are fixed (1-20), so the result is deterministic. The tests read the truth from the in-memory plan
    rather than from git, for speed; `test_truth_rows_match_the_manifest` checks that it is the manifest's.
40. **The statistic:** ten equal-count deciles of unit files by loc at the snapshot (ties by file id); in each,
    Spearman's rho (average ranks for ties) between density at the snapshot and true fixes after it; deciles
    where either side is constant are dropped; mean over deciles, then mean over seeds 1-20. Test 5 checks every
    property (6 for Python, 8 for C). Test 6 uses beta = 0.25, 0.5, 1.0 on branches; "clearly positive" = mean >
    0.03 and mean / SE > 4 at each strength; the means must increase.
41. **Test 4** runs `tools/sa3_nesting.py`'s own `nesting()` and `grammar_for()` on every code file at both
    points, with an interpreter whose `tree_sitter_language_pack` is exactly the version the tool pins (1.20.0):
    `$CONTROL_REPO_TS_PYTHON` if set, else the interpreter running pytest; otherwise it skips and says why. On
    this machine `/usr/bin/python3` has 1.20.0 (the selfscan venv has 1.21.0 and is not used).
42. Beyond the spec: the planted counts are checked for **every** code file at **both** points (not a sample),
    with independent readers (Python `tokenize` and `ast` for branches, nesting, state writes, calls out and in;
    regexes for C branches, calls, pointer and allocation operations); C files are compiled with
    `gcc -fsyntax-only` when a compiler is present.
43. **Runtime** of the whole file on the development machine: see the end of this file (51).

## Revision 2 (after the first review, `docs/process/reviews/control_repo_review_fable.md`)

44. **Positives are snapshot unit files** (finding 1). Each label's `positives` lists `{id, path_at_snapshot}`
    for unit files that exist at the snapshot, and only those; unit files the commit touches that were created
    later go in `touched_unit_files_not_at_snapshot` and are never positives. The tree-wide rule counts the
    snapshot's unit files among those touched, against the snapshot's unit count.
45. **A revert of post-snapshot code that quotes a ticket** (finding 2) is listed under `ambiguous` with the
    readings `reference_counts` (counted, through the quoted reference) and `nonqualifying_revert` (not counted).
    Direct and squash commits: ambiguous only if nothing else in the commit carries a link (another link decides
    it). Inside a merge the two revert readings are crossed with the four merge readings (names like
    `inherit + reference_counts`); a same-merge revert that quotes a ticket is a link the merge may not inherit
    under `inherit` (and taints), and is inheritable under `taint_governs_control_pool_only`, as in the code,
    where only the revert kind is excluded for a target inside the merge.
46. **The fourth merge reading**, `taint_governs_control_pool_only` (finding 4), follows
    `tools/sa3_outcomes.py` lines 221-310: a merge counts when its first-parent diff shares a file with a linked
    brought-in commit that is not a bot's; fix-worded or non-qualifying brought-in commits do not stop it (the
    taint there only keeps a merge out of KW and the control pool). Merges bringing in both a linked and a
    fix-worded commit are therefore ambiguous now (6 at seed 11, default profile; before: decided not counted).
    "Shares a file" is read over all files of the merge diff; positives are its snapshot unit files.
47. **The change effect** (finding 7): at least 40% of unit files change branch density in the prior year, with
    the sign a fair coin (21). Scheduling is from each file's own stream and never looks at structure, size or
    busyness, so neither the activity it adds nor whether a file is scheduled depends on a planted property or
    on busyness; whether a scheduled file can move depends on having a removable branch unit (the same for both
    signs). Measured realised share: default profile seeds 1-5, Python 0.64-0.70, C 0.52-0.60; small profile
    seeds 1-20, Python 0.58-0.83, C 0.47-0.69 (seed 11 default Python: 0.681; before r2 0.09). Over seven
    default seeds per language, Python 726 files up / 660 down, C 621 / 570, and no realised direction differed
    from its coin. The null on fresh seeds after the change (40 seeds, 800 files): d_branches Python +0.0022 (SE
    0.0065), C -0.0074 (0.0074). The planted effect is still recovered: d_branches = 0.5 reads +0.170 (SE
    0.013, 20 seeds, 400 files). Because the snapshot's branch density = prior density + change, a planted
    `d_branches` effect now also shows on `branches` (+0.086 in the same run).
48. **Caller edits** (finding 3, spec r2): `commits[].caller_edit_ids` lists the files a base-history rename or
    delete edited only as callers. The inserted renames of `renames_after_snapshot` have none (34).
49. **C pointer declarations** (finding 8, spec r2): every C file records `pointer_declarations` (the `long *data`
    parameter of each definition, prototype and extern, and the locals `long *cursor`, `long *buf`) beside
    `pointer_ops` (dereference writes). `pointer_mapping` in the manifest says which an instrument is expected to
    see: a keyword family counting pointer syntax sees both; a measure of pointer use, `pointer_ops` only. The
    engine's mapping is not known to the generator.
50. **Density is rank-related to size inside a band** (finding 5), and that is a property of integer counts, not
    of the generator's formula: among files of one decile with the same count, density falls as loc rises, so
    Spearman's rho of density against loc is negative inside deciles (measured, default profile, seeds 300-311:
    Python -0.04 to -0.08, C -0.03 to -0.10), while the planted densities show none (within +-0.03). Fixes rise
    with loc (loc^a), so the band statistic inherits a small negative push. Not removed: a count that is a whole
    number of lines cannot avoid it, and the size term is the spec's. Stated in README.md for phase 2.
51. **Versions and runtime.** (r2) Manifest schema 2, generator 1.1.0; (r3) schema 3, generator 1.2.0; (r4) schema 4,
    generator 1.3.0. The whole test file, wall
    clock on the development machine: 45 passed in 131 s (r4; 39 in 128 s at r2) (the statistics tests take about 115 s of it, in two
    worker processes; about 4 CPU-minutes in all).

## Revision 3 (owner ruling, 2026-11-14)

52. **Tainted merges follow the code.** Every first-parent merge's `counted` and `positives` are decided by the
    reading `taint_governs_control_pool_only` (46). The manifest states the ruling once, at top level
    (`rulings`: date, text, what it covers, what it does not), and the clause of every merge label begins
    "[decided by the owner ruling of 2026-11-14: tainted merges follow the code]" (over-cap and tree-wide merges
    included: the code does not count them either). The other three merge readings are kept on the label as
    `unruled_readings` (each marked `ruled: false`) whenever they would give a different count or positives.
53. **Still open:** a brought-in revert of post-cut code that quotes a ticket (45) is not ruled. Such a merge is
    listed under `ambiguous` with the ruled merge reading crossed with the two revert readings
    (`taint_governs_control_pool_only + reference_counts` / `+ nonqualifying_revert`), plus its unruled
    readings; direct and squash commits are unchanged. Under the ruled reading a same-merge revert's revert link
    is not inherited, but a ticket it quotes is (as in the code, where only the revert kind is excluded); that
    is why a quoting same-merge revert is also left open.
54. Measured, seed 11, default profile, `merge_workflow`, 285 first-parent commits after the snapshot (all
    merges): before r3, 0 counted / 196 not counted / 89 ambiguous; after, 88 counted / 196 not counted / 1
    ambiguous (a merge bringing in a late revert that quotes a ticket). The 6 merges that bring in a linked and a
    fix-worded commit are all counted.

## Revision 4 (after the first harness run, `docs/process/harness_report.md`)

55. **Linguist names.** Every name the generator can produce was checked against the cached `vendor.yml` and
    `documentation.yml` (Linguist e0c78d62c42a), as a directory at each depth and as file names (all noun x role
    stems, with the `test_` and `mini_` prefixes), plus every fixed or mutation-added path. Collisions found:
    - the directory word `cache` (`(^|/)cache/`): a base collision; replaced by `memo` in `codegen.DIR_WORDS`.
      Nothing else in the word lists (directories, file nouns, roles, verbs, doc nouns) matches;
    - planted on purpose, non-units, matching as intended: `vendor/thirdparty/` (three vendor patterns),
      `docs/` (`^[Dd]ocs?/`), `LICENSE`, `README.md`, `.gitattributes`;
    - mutation-added: `tests/fixtures/generated/` (`test_fixtures`) matches `(^|/)[Tt]ests?/fixtures/`, intended
      (they are test inputs, `is_unit` false); `docs/imported/` (`huge_import_merge` notes) matches
      `^[Dd]ocs?/`, intended (documentation); `src/contrib/<lib>/` (`vendored_half`) matches nothing, intended
      (that is the fault it plants); `native/`, `scripts/` (`mixed_language`), `experimental/`
      (export-ignored), `libmini`, `generated/` alone, `requirements.txt`, `deps.txt`, `gen_tables.*`: no match.
    The avoid-list `codegen.LINGUIST_AVOID` holds the names a generator could plausibly pick, each with its
    pattern; `history.check_linguist_names` refuses a base layout that uses one outside the planted places. The
